## 4. 啟動 T4 GPU 完整測試所需前置條件與清單

若要在 GPU 環境（如 Colab T4 或配備 NVIDIA GPU 之執行個體）開始正式跑測，需具備以下資源：

1. **GPU 執行環境**：
   - 配備 NVIDIA T4 GPU（16 GB VRAM）之環境。
   - NVIDIA Driver 與 CUDA Toolkit（建議 CUDA 12.6 或 13.0）。
   - 支援 NVDEC 與 NVENC 之 FFmpeg（可用 `ffmpeg -encoders | grep nvenc` 確認）。
2. **PyTorch 與 TorchCodec CUDA 建置版本**：
   - `torch >= 2.11`（帶相應 CUDA 標籤，例如 `+cu130` 或 `+cu126`）。
   - `torchvision >= 0.26`（與 PyTorch CUDA 版本嚴格相符）。
   - `torchcodec == 0.17.0`（CUDA 版本，需能載入 `libtorchcodec_image.so` 與 `libnvrtc.so`）。
3. **來源素材檔案**（需置於測試機並校驗 SHA-256）：
   - `video-170s.mp4`（170.87 秒，4K 60 FPS，10,252 幀）。
   - 固定鏡頭 242.62 秒影片（1080p 60 FPS，14,557 幀）。
4. **模型權重 Checkpoints**（需置於測試機並校驗 SHA-256）：
   - `yolo26n-seg.pt` (`361fbfabab285c3237700b6bb91d7ecfa602cd945fffda8dbe1242829b71e73f`)
   - `yolo26n-pose.pt` (`eb3bb8268828aeaf515cec23a4bfafd793944a86fe9af94ba7823609c14522a9`)
   - `deepgazemr-ledov.pt` (`db0e3c4738664a6e8026229b8d1a74edda9ea1d571432273018a13c88a2c8ec6`)

## 5. 基於報表與資料流之效能優化提案

根據現有程式碼架構（`reframe/pipeline.py`、`reframe/frame_pixels.py`、`reframe/saliency/backends/deepgazemr.py`、`reframe/perception/tensor_yolo.py`）及測試資料流分析，提出以下 5 項具體優化方案：

### 提案 1：DeepGaze 觀測串流與 GPU 預處理異步化（針對 M6 與 M3B）
- **現象與瓶頸**：
  在 `TensorDeepGaze` 中，觀測影格以連續 16 幀批次存入 ring buffer。目前預處理（正規化至 ImageNet 均值標準差）與推論在主執行緒中串行執行。當累積到 16 幀或需要執行 forward 時，主執行緒等待張量轉換。
- **優化方案**：
  配置專屬 CUDA Stream，在每幀由解碼器送出時，非同步在 GPU 端執行 float 轉換與正規化寫入既有 ring buffer，使資料預處理耗時隱藏在主線程 YOLO/Pose 推論時間內。
- **風險與防護**：
  嚴格保留 16 個連續影格之原順序與時間窗口一致性，不改變任何數學運算；在需要 forward 前執行 stream 同步，防止資料競爭。

### 提案 2：CUDA Sampled Bilinear 縮放下採樣核心合併（針對 M5）
- **現象與瓶頸**：
  4K 影像下採樣至 384 或 YOLO 輸入尺寸時，若使用 PyTorch 內建 `grid_sample` 或雙線性內插，會建立大型 float32 暫存張量（4K 影像一個 float32 張量即需約 99 MB 顯存）。
- **優化方案**：
  現有實作已有初步取鄰點暫存機制（`reframe/frame_pixels.py`），可進一步使用自訂或緊湊型 CUDA 算子，將「整數步長網格提取」與「雙線性插值權重計算」在單一 kernel 中完成，直接以 uint8 輸入輸出 uint8 或 fp16，使 4K 顯存峰值進一步降低。
- **風險與防護**：
  需嚴格維持像素誤差 ≤ 1/255 之驗收標準，並保持 CPU fallback 行為不變。

### 提案 3：Pose 推論多候選人 Batch 化聚合（針對 M3A 與 P1）
- **現象與瓶頸**：
  在雙人交錯、搶鏡或背景存在競爭者時，若有多個候選人的 Pose ROI 需要更新，目前 `YOLOPoseHelper` 依 `pose_batch_size` 進行分批，但不同大小的 ROI 需在 CPU/GPU 進行個別 letterbox。
- **優化方案**：
  在 GPU 端直接將多個候選 ROI 座標映射後，透過 GPU batch letterbox 聚合為單一 `[N, 3, 256, 192]` 張量，進行單次 Pose forward。
- **風險與防護**：
  需確保座標反算時精確對齊各候選人於原圖之絕對座標，且主角 ID 優先權順序不被重排。

### 提案 4：TorchCodec NVDEC Zero-Copy Tensor Pipeline（針對 M2 與 Stage2）
- **現象與瓶頸**：
  Stage2 旨在消除 host-device 拷貝。但若解碼輸出格式為 NV12，仍需在 GPU 上執行色彩空間轉換（NV12 -> RGB）。
- **優化方案**：
  確保 NVDEC 輸出直接在 CUDA 裝置顯存完成色彩矩陣乘法，輸出為連續通道張量，直接餵入 Tensor YOLO Predictor，完全避開主機記憶體（CPU RAM）反覆配置。
- **風險與防護**：
  需透過 `video_io.pixel_metrics` 嚴格監控 `cpu_materializations == 0`，並確保色彩矩陣轉換與 OpenCV/reference 色彩誤差在容許閾值內。

### 提案 5：自適應跳幀窗口動態穩定評估優化（針對 P3 與方案 B）
- **現象與瓶頸**：
  目前 balanced profile 上限為 6 幀（60 FPS 下為 0.1 秒最大年齡），在穩定幀時依光流和姿態穩定度逐步延長至 4 幀與 6 幀。但目前光流採用稀疏或全域平移評估。
- **優化方案**：
  利用主角主軀幹遮罩質心位移作為主要動態指標，若質心加速度低於閾值且遮罩形狀殘差極小，可平滑將間隔保持在安全上限；反之若偵測到加速度突變，在光流判定漂移前提前觸發偵測。
- **風險與防護**：
  真實量測秒齡（seg_max_age 0.1 秒）與肩髖 3 點幾何門檻不可放寬，維持方案 B 安全邊界。
